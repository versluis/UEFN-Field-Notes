# LORE (Revision Control)

Branches, merging, file locking, logs, and working rules for Epic's built-in, server-hosted revision control. LORE was named **Unreal Revision Control (URC)** before v42 — older docs and forum threads use that name. Much of this is undocumented by Epic and was established by testing on a deliberately throwaway project; the deep-dive forensics write-up — the three silent merge failures, the log archaeology, the conflict paths and the multi-user lock lifecycle — is in [06a-lore-branching-and-merging.md](06a-lore-branching-and-merging.md).

## Basics & working rules

- Commit at every stable milestone; "Restore as Latest" discards broken history back to the last good commit.
- **Commits and restores are all-or-nothing (v42, verified 29 Aug 2026).** No per-file commit selection, no partial restore. VS Code's Lore panel shows history and read-only older text-file versions; sync/commit/restore happen only in UEFN.
- ℹ️ **`Lore.log` is ROTATED, not wiped** (verified 3 Sep 2026 — corrected 3 Sep 2026, shortly after the first and wrong version of this note). An engine update starts a fresh `Lore.log`, but **the previous one is preserved beside it** in the same `Saved\Logs\` folder as `Lore.log-backup-<timestamp>` or `Lore-backup-<timestamp>.log` (same pattern for `lore-vscode-plugin.log`). Verified: a v42.10 install left a fresh 1.9 KB log sitting next to a **2 MB backup still holding the entire previous session**, failed-merge errors and all. **If a LORE log looks empty, find the backup before concluding the history is gone.** ⚠️ They are ordinary log files with no stated retention — copy one out of the folder if a finding depends on it. ✅ **The v42.10 update did NOT bump the LORE client, so v42.00 branch findings carry over unchanged** — both versions run `0.8.6-nightly+331_3664`.

## 🔍 Branches (found by accident 29 Aug 2026 — not in the docs)

Bottom toolbar → *Revision Control* → **Branch Explorer**: a commit graph with *New Branch*, *Merge From*, *At Latest*, *Refresh View*, *Dock in Layout*. With only `main` present, *Merge From* shows greyed out — presumably because there is nothing to merge from; not yet confirmed *(confirmed in effect 3 Sep 2026: with a second branch present, Merge From activated and real merges ran)*. **Intended use: experiments that may be thrown away — branch, test, merge or abandon, as in Git.**

- ⚠️ **UNVERIFIED — run these three checks before trusting a branch with real work:** **(1)** Branch off, change one property, commit, switch back to `main` — is `main` untouched, and does the branch carry **binary assets** (the `.umap`, character definitions) as well as Verse text? **(2)** Does switching branch swap the **working copy on disk** — so `VerseToolset.ReadFile` and VS Code's Lore panel follow the editor — or is it editor-side only? If an agent reads `main` while the editor sits on a branch, there are two truths again. **(3)** Change the `.umap` on both `main` and the branch, then *Merge From* — does LORE merge, take one side, or refuse? **Until (3) passes, branches are for abandon-or-merge-clean experiments only, never for a build that must come back.**
- ✅ **(1) and (2) ANSWERED 3 Sep 2026**, on a throwaway project deliberately. **(1)** `main` stays untouched, and the branch **does** carry binary assets — a `FortStaticMeshActor` `.uasset` and a brand-new material asset both crossed intact. **(2)** Switching branch **does** swap the working copy on disk: files under `__ExternalActors__` and a content folder appeared and vanished as the editor switched branches, verified by reading them straight off disk rather than through the editor. **No two-truths problem.**
- ✅ **CHECK (3) ANSWERED 3 Sep 2026 — branches are now safe for work that must come back.** A deliberate same-line conflict was staged in a `.verse` file on both branches from a shared ancestor. **LORE neither silently merges nor refuses.** It performs a genuine **three-way merge**: it materialises `<file>~base`, `<file>~mine` and `<file>~theirs` beside the working file, logs `Branch diff found 0 changes and 1 conflicts` and `Merged as text with conflict markers`, blocks with a *Conflicting Changes* modal, then opens a **Conflict Resolution** tab offering per-file `All Current` / `All Incoming` plus a hand-off to **VS Code's 3-way merge editor**. Resolving to keep **both** sides worked, and the `~base`/`~mine`/`~theirs` files are **cleaned up automatically** on resolve. **Conflicting edits are detected and surfaced for review, never silently resolved.**

## 🔒 File locking (proven with two accounts on two machines, 4 Sep 2026)

**LORE HAS FILE LOCKING, and it changes how a team should work.** **A per-file lock is taken the moment you SAVE — not when you commit — and it is enforced, not advisory.** Attempting to edit an asset another user has open produces *"cannot edit… checked out by another user… changes will be automatically rolled back"*, a toast naming the holder, and an actual **`Undo: Transform`**. **Locks release on check-in or branch switch**, in bulk. **They are branch-scoped** — two people on *different* branches do not contend at all.

- ⭐ **Therefore: on a shared branch, binary conflicts are IMPOSSIBLE by design** — you are blocked before you can create one. The thin binary-conflict UI below is the **cross-branch fallback**, not the normal path.
- ⭐ **Choose the collaboration model by FILE TYPE, not by Git habit.** Verse merges properly at line level, so **branches are cheap and safe for code**. Binary assets cannot merge at all, so a **shared branch with locks is strictly better for level and actor work**. Same branch = you can be blocked but never lose work; separate branches = never blocked but someone's work gets discarded at merge. This is close to the opposite of the usual Git instinct.
- ℹ️ **Outliner vocabulary:** 🔒 red padlock = locked by someone else; ✅ green tick (*"item has been modified"*) = you hold the lock; `*` = unsaved. A locked object also **greys out in the viewport when unselected** and shows its true material when selected.
- ⚠️ **The blocking dialog names the level, not the actor** — it reports `…:PersistentLevel` while the Outliner correctly pins the lock to the individual actor. Read only the dialog and you would think the whole level was locked.
- ⚠️ **Lock state replicates live; CONTENT DOES NOT.** You see the padlock within seconds but never the other person's work until they check in and you sync. This is the opposite of the old **Multi-User Editing (Concert)** plugin, which replicated edits live. LORE is not showing you work in progress — it is preventing collisions.
- ✅ **Stale locks ARE recoverable — there is a self-service override (verified 4 Sep 2026).** Locks are **server-side and survive the holder closing UEFN entirely**, and they also survive *other* people's check-ins. But **right-click the locked asset → Revision Control → `Unlock`, or `Unlock all (<username>)`** to force-release another user's locks, named per holder. ⚠️ **The blocking dialog under-sells this** — it says only *"coordinate with your teammate to check them back in,"* implying no override exists. It does. ⛔ **Use it as a judgment call, not a reflex**: force-unlocking removes the protection around someone's *uncommitted* work.
- ℹ️ **Check-in releases only YOUR OWN locks.** The bulk release is scoped by identity — `LoreLockFileReleaseArgs { paths: [], owner: , owner_id: <you> }` — so another user's locks are untouched. **You can commit normally while a teammate holds a lock on a different asset** (verified: a check-in succeeded and moved the branch ahead while a foreign lock persisted).
- ✅ **A pull arrives as a LIVE SERVER PUSH**, not polling — a persistent gRPC notification stream, surfaced as a nudge. It is **advisory only**: nothing touches your working copy until you act. The toolbar button **renames itself** from `At Latest` (greyed) to **`Sync Latest`** (green); the pull is `lore::revision::sync`. ⚠️ **`is_remote_ahead` lags** — it still read `1` after a completed sync with revisions matching. **Compare `revision_number` to `revision_remote_number` instead.**
- ℹ️ **Moving a project to team space does NOT re-point the local clone** — repository ID, `remote_url` and instance ID were unchanged, no restart needed. The only trace is a silent notification unsubscribe/subscribe cycle in the log.

## ⛔ Binary conflicts (tested 4 Sep 2026) — there is NO "keep both"

A shared-ancestor actor was moved **sideways on one branch** and **up on the other** — two legitimate, non-overlapping edits. Text conflicts let you resolve to a result *neither* branch had; **binary is a radio button: Current or Incoming, and the other side's work is destroyed.** LORE cannot merge two edits to one binary asset, only choose between them. ⭐ **Working rule for a second seat: coordinate who owns which actors.** With One File Per Actor, two people editing *different* actors is safe (their changes are separate files and auto-merge); two people editing the *same* actor means one of them loses work, every time.

- ✅ **Non-conflicting changes still merge through a conflict.** The same merge reported `Branch diff found 4 changes and 1 conflicts` → `Realize 4 changes` → `Realized non-conflict changes`. A newly added actor came across cleanly while the moved one conflicted. **One conflicting file does not block the rest of the merge.**
- ℹ️ **Binary takes a distinct code path and produces different artefacts.** Log says `Merge identified binary file for unresolved conflict` (text says `Merged as text with conflict markers`). Binary writes **`~base` and `~theirs` but NO `~mine`** — because "mine" is the live working file, which is why the current version's card reads *"Loaded in level"*. The choice is recorded as its own command: `lore::branch::merge_resolve_theirs`.
- ⭐ **UEFN gives a genuine VISUAL diff for binary conflicts** — side-by-side thumbnails with size, date, revision ID and description, grouped per asset in a collapsible list so multiple conflicts can be cherry-picked individually, plus `All Current` / `All Incoming` bulk buttons.
- ⚠️ **…but the visual diff is close to useless for transform changes.** Both thumbnails were **identical** — a moved sphere still looks like a sphere. It only helps when the *appearance* changed (material, mesh). For position/rotation/scale you are choosing blind.
- ⚠️ **The "Description" on each card is the REVISION message, not a description of that file's change — and it actively misleads.** In testing, the incoming card described a *different asset's* addition, because that was the head revision's message. **Do not use it to decide which side to keep.**
- ⭐ **"Reload level to preview" is load-bearing, not cosmetic** — it **rewrites the working file** with the selected version so you can see it in the viewport. Since binary has no `~mine`, during resolution *your own version exists nowhere on disk* — only in LORE history. **Previewing is the only way to see what you are about to accept.**
- ⭐ **The "Resolve Conflicts" confirmation dialog is the ONLY place LORE warns that work will be destroyed** (*"your local conflicting changes will be overwritten by those from latest revision"*). It is suppressible via *Don't show this again*. ⛔ **Do not suppress it.** For text you can inspect the merged result afterwards; for binary it is the last checkpoint before a one-way loss you cannot see in any diff.

## The merge & resolve workflow — the steps that are easy to miss

- ⚠️ **Conflict resolution is a THREE-step commit, and the middle step is easy to miss.** Editing and saving in VS Code is **not** enough — the commit option stays unavailable until you click **Resolve** in UEFN's Conflict Resolution tab (`lore::branch::merge_resolve`, which flips the file's node flags from `3129` *Conflicted* to `7225` *Resolved*). Only then does Check In become available.
- ⛔ **Resolve is a declaration, not a validation — this one can lose work silently.** Log-verified: `merge_resolve` marks the file resolved **regardless of whether you actually merged anything**. It fired once while the working file was still byte-identical to `~base`. Checking in at that moment would have committed the **ancestor** and discarded *both* sides' changes, with no warning. **Confirm the Result pane reads zero conflicts remaining, and contains what you intend, before clicking Resolve.**
- ℹ️ **In VS Code's merge editor both top panes are titled `<file>`**, because LORE passes three files of the same name — the usual Current/Incoming labelling is **not** reliable here. **Identify the panes by their content.** The bottom **Result** pane is a normal editable editor, which is the simplest and most predictable way to keep both sides (mind Verse's significant indentation when hand-editing).
- ⚠️ **A LORE merge is a two-step commit, and the second step is easy to miss.** *Merge From* lands the result on a **personal backup branch**, not on the destination branch; **Check In Changes** then promotes it and archives the backup. **Blue icon in Branch History = pending, tick = at head.** Also check in until you see the tick *before* starting a merge — LORE's own auto-backup can strand an unpushed commit that blocks it (`Branch has been advanced by another instance`).
- ⛔ **A failed merge aborts silently.** `merge_abort` rolls everything back, the level looks untouched, and the UI gives no error worth the name. Three identical retries taught nothing; one log read explained it. If a merge "did nothing", read `Lore.log` (see log-rotation note above for where to find it).
- 🔍 **`Branch has been advanced by another instance` never means a real teammate.** A genuine second seat announces itself as a live notification and a `Sync Latest` prompt. This error is always **self-collision** — your own stranded auto-backup commit — which turns a scary-sounding message into a one-line diagnosis: check in until you see the tick, then retry.
- ⭐ **Skipping revision numbers are normal, not evidence of missing work.** Auto-backup and merge commits live on personal backup branches and are hidden from the branch-filtered history, so the visible numbers jump. ⚠️ Observed on LORE `0.8.6-nightly` (Sep 2026) and **not** verified against older (June 2026) history — treat as a strong hypothesis for historical gaps, and read rather than restore when doing archaeology.
- ⚠️ **Renames merge as redirectors.** Renaming a material left a 1.3 KB `ObjectRedirector` at the old path with the referencing actor still pointing at it, and **the redirector merged across intact**. Run *Fix Up Redirectors* before merging if the destination branch should be clean. *(v42.10 widened automatic redirector placement to Verse files — see [00-version-watch.md](00-version-watch.md).)*
